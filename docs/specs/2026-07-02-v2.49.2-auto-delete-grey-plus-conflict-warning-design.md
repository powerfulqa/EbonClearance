# v2.49.2 - Auto-delete grey on loot + conflicting-addon warning

**Status:** approved for implementation
**Date:** 2026-07-02
**Version target:** v2.49.2 (patch - additive schema only, no removals)
**Depends on:** v2.49.1 (autolearn correlation, bug-report shape)
**Feeds into:** v2.50.0 (peer-share broadcast, still parked)

## Two independent features in one patch

Both features add a checkbox to the Delete Settings panel, both are additive DB fields with nil-defaults, and both fire off existing event hooks (PLAYER_LOGIN, BAG_UPDATE). Grouping them into one v2.49.2 stanza reduces release-cycle overhead and keeps the Delete Settings changes together.

---

## Feature 1 - Auto-delete grey items on loot

### Goal

Give the player an opt-in toggle that immediately destroys grey (quality 0) items as they land in bags. Rationale: while farming, bag space matters more than the ~10 copper a grey vendors for; the player would rather trash the grey to keep slots open for green+ drops.

### Why not use the existing Delete List?

The Delete List is per-itemID and grows manually. To auto-delete every grey drop the player would have to add every grey itemID individually - unmaintainable. This new toggle uses the item's quality field directly, so any grey with a positive sell price qualifies without manual list-tending.

### Architecture

- **New DB toggle:** `DB.autoDeleteGreyOnLoot` (per-character, default `false`).
- **New scan pass** in the existing BAG_UPDATE debounce alongside the loot log + auto-mark-Resilience + auto-mark-affix-dupes scans.
- **Same delete plumbing** as `autoDeleteOnPickup` - a single PickupContainerItem + DeleteCursorItem cycle per BAG_UPDATE burst, serialised via the existing delete-popup mutex.

### Gates that qualify an item for auto-delete

All of these must be true:
- `DB.autoDeleteGreyOnLoot == true` (opt-in)
- `DB.enableDeletion == true` (master switch)
- `quality == 0` (grey junk)
- `sellPrice > 0` (a grey with sellPrice=0 is likely a quest item or key)
- NOT in `DB.blacklist` / `ADB.whitelist` / `DB.blacklistAuto` (respect all Keep List variants)
- NOT in `DB.deleteList` (the manual delete path handles those)
- NOT `IsEquippedItem(itemID)` (defensive - grey equippables aren't a real case but the guard costs nothing)
- NOT a quest item (`GetItemInfo` returns `itemType == "Quest"`)

Any gate failing = the item stays in bags, falls through to normal sell rules.

### Vendor-open exception

If a merchant is open when the scan fires (`MerchantFrame:IsShown()`), skip the auto-delete for this pass. The vendor round-trip is imminent and yields more copper than a delete. Grey items sell for a stack of copper each; even fractional copper adds up over a farming session. Once the merchant closes, the next BAG_UPDATE fires and the auto-delete runs.

### Toggle placement

Delete Settings panel, positioned immediately after `Auto-delete on pickup` (they're conceptually adjacent - both are "delete on arrival" flows). Grey explanatory note beneath: "Grey items destroy the instant they hit your bags. Skips vendor copper; keeps bag slots open. Never touches keep-listed items, equipment, or quest items."

### Sanity gates

- Never runs if `DB.enableDeletion == false` - master switch has final say.
- Never runs on greys with `sellPrice == 0` - avoids trashing quest keys or 0-value miscellaneous items.
- Never runs on equipped items - defensive guard.
- Blacklist / Keep List / auto-blacklist all veto.

### Chat feedback

Existing `DB.announceDeletions` toggle governs whether individual auto-deletes log a chat line. No new chat setting needed. Follows the same "one line per delete" pattern as `autoDeleteOnPickup` when the announce toggle is on, silent when off.

## Feature 2 - Conflicting-addon warning

### Goal

When EC's delete path is active AND a third-party auto-delete addon is also loaded, alert the player once per session so they can resolve the conflict before it manifests as unexpected item loss or delete-popup contention.

### Why now

Real-world reports of item loss when two auto-delete addons are running have surfaced across the 3.3.5a community. EC's delete path uses `DELETE_ITEM_CONFIRM` + `StaticPopup1EditBox` + `PickupContainerItem` - a race can drop items into the wrong basket.

### Architecture

- **New DB toggle:** `DB.warnConflictingAddons` (per-character, default `true`). Opt-out so the warning is on by default the moment the conflict is detectable.
- **Detection helper:** `EC_HasConflictingDeleteAddon()` returns `IsAddOnLoaded("AutoDelete")` truthiness. Local variable + code comment use neutral framing ("third-party auto-delete addon"); only the `IsAddOnLoaded` folder-name string is specific, per the CLAUDE.md exception for necessary detection code.
- **Chat warning at PLAYER_LOGIN** (one-shot per session), gated on:
  - `DB.enableDeletion == true` (EC's delete path is active - otherwise there's no conflict to warn about)
  - `DB.warnConflictingAddons == true` (player hasn't opted out)
  - `EC_HasConflictingDeleteAddon() == true`

### Warning copy (neutral framing per project rule)

```
|cffff4444[EbonClearance]|r Another auto-delete addon is running.
Both may try to delete items, and the delete-confirm popup can get
contested. If items disappear unexpectedly or delete popups
misbehave, disable one of the two. Silence this warning: uncheck
'Warn about conflicting addons' in Delete Settings.
```

- No third-party addon named in the message. Player identifies which one via their own addon list.
- Localised via `L[]`; frFR + deDE templates get the English key with an empty value.

### Toggle placement

Delete Settings panel, at the bottom of the toggle list (least likely to be flipped in normal play). Grey explanatory note beneath: "One chat message at login when EC detects another auto-delete addon running. Off = silent even when a conflict is detected."

### `/ec bugreport` line

Under Environment Capabilities section (already contains "Host bag UI detected"), add:
```
Third-party auto-delete addon detected: yes/no
```

The existing Loaded Addons dump further down in the report already lists every addon by folder name, so the maintainer sees both the neutral flag AND the specific folder name in the same report.

## New schema (both features)

```lua
-- EnsureDB additions (per-character, initialised by EnsureDB):
if type(DB.autoDeleteGreyOnLoot) ~= "boolean" then
    DB.autoDeleteGreyOnLoot = false
end
if type(DB.warnConflictingAddons) ~= "boolean" then
    DB.warnConflictingAddons = true
end
```

Both are additive with nil-defaults. Existing v2.49.1 saves migrate on next load without needing a wipe.

## Non-goals

- **Auto-delete white / green / blue items on loot.** Grey has a clean quality-check gate; higher rarities would need iLvl gates and per-rarity toggles that the existing quality-rule sweep already handles at the vendor. Out of scope.
- **Named callout of the conflicting addon.** Project rule prohibits it in user-facing text; the reporter can identify it via their addon list.
- **Deep dedup with the AutoDelete plugin's rules.** Both addons run their own logic; the warning surfaces the situation, resolution is the player's choice (disable one, tune the other).
- **Bump the conflict-warning to a StaticPopup or persistent banner.** Deferred; the one-shot chat line is enough for v2.49.2. If reports show it gets missed, revisit in a later patch.
- **Peer-share of "I saw AutoDelete on this player."** Out of scope; player privacy > telemetry.

## Ship classification

Patch release. Both toggles are additive with nil-defaults. `DB.autoDeleteGreyOnLoot` defaults false (destructive-off-by-default per project rule); `DB.warnConflictingAddons` defaults true (informational, low noise, opt-out available). Feature-flagged so existing behaviour is unchanged for v2.49.1 users on upgrade.

## Risks

1. **Auto-delete grey false positive.** A misconfigured server could stamp `quality = 0` on a valuable item. Mitigations: `sellPrice > 0` gate (prevents trashing 0-value curiosities), Keep List veto (player can protect specific greys), quest-item gate. `DB.enableDeletion` master switch is the final safety net.
2. **Merchant-open race.** If BAG_UPDATE fires the moment before the player opens a vendor, greys could be deleted a fraction of a second before the vendor visit. Mitigations: `MerchantFrame:IsShown()` check inside the scan short-circuits the run when a merchant is open. If the timing edge case ever surfaces, add a 0.2s post-MERCHANT_SHOW cooldown - out of scope for v2.49.2 ship.
3. **Conflict warning misses a similarly-named addon.** Only `AutoDelete` folder name is checked. If a fork ships under a different folder name, it goes undetected. Acceptable; the warning is a nice-to-have safety net, not a hard prerequisite.
4. **`DB.enableDeletion == false` bypass.** Both features gate on this. Player who wants greys auto-deleted but not the Delete List can't have grey-auto-delete without also enabling the master switch. Acceptable trade-off - simpler mental model.
